# Bible: skill details page UI and behaviour

Part of the Bible rulebook (core rules: [12t_projects/bible/CLAUDE.md](../../../12t_projects/bible/CLAUDE.md)).

## Phone layout
* **Phone layout (<900px, `html.tool-wide-hero`):** no `fitStageToScreen()` scaling; page scrolls; one column (search + card + related first, stats panels after via `order:1`); Test popup fixed at `top:26vh`; stat tooltips under the value (`positionStatTooltips()`); `.view` `animation-fill-mode:none` (its transform would break `position:fixed`). <560px: LCK-variance and Final chips full width; the preset swap pop-up table puts each label on its own line above the 4 numbers. At ≤900px the hero card shows round ‹ › buttons (`.sk-skill-nav`, `data-step` ±1) beside the skill icon that call `navigateSkill()`, the same as the ← / → keys; disabled at the first / last skill, hidden on desktop. The document ← / → handler stands down while typing in a field, while the PRESET window is open, behind any open `[aria-modal="true"]:not([hidden])` pop-up (☕ with its arrow-key tabs, credits pager, changelog, mechanics) and for a key another handler already took (`e.defaultPrevented`); the validator checks the last two (review fix 2026-10-23: the ☕ tabs' arrows switched the skill behind the pop-up). **No unasked keyboard on touch screens (2026-10-05, user):** code never focuses a text field the user did not tap through plain `.focus()`; use `softFocus(el)` (top of the main script), which skips under `(pointer: coarse)` (tool open, class browser, PRESET window name field). Focusing buttons is fine.

## Delta motion and dependency strip
* **Delta motion (2026-10-05):** `renderHero()` is a wrapper: `heroSnapshot()` → `renderHeroNow()` (the real rebuild) → next frame `heroDelta()`. Changed `.sk-stat` / `.sk-dmg` chips, `.sk-cost-badge`s, desc `.sk-val`s and desc `[status]` keywords get `.sk-delta` (chips: one flash with the glow kept inside, a tinted fill + inset edge glow, no ring outside the chip, user 2026-10-05; desc text: gold flash); tooltip text counts as part of a field, so a tooltip-only change also triggers. A `button[data-dep-id]` whose rank, on-state or icon changed flips. Better (rank up, or on): `.sk-dep-flip-on` and a three-dot gold comet (`.sk-shot`, WAAPI arc) flies from the icon to every changed field, nearest first, pinging it on impact. Worse (rank down / off): each field flashes red (`.sk-delta-down`), a red comet (`.sk-shot.is-red`) flies from it back into the icon, and the icon's `.sk-dep-flip-off` is delayed so it turns grey as the last one lands. With no dep source, a **server switch** sends gold comets from the newly selected server button (`.sk-server-deps .sk-server-btn[data-server]`) to every changed field, pinging on impact; the server is compared with `serverSeen` (the value at the end of the last rebuild, because the buttons set `currentServer` before calling `renderHero()`), and while the server pop-up is open the whole comparison is held, so they fly when it closes. Otherwise, if exactly one stat input (player 8 + LV, enemy 8; `statInputs()`) changed, comets glow in that stat's `--stat-<key>` colour and fields ping with `.sk-delta-stat` (`--delta-c`); a higher player stat is "better" by default and a higher **enemy** stat "worse" (user 2026-10-05: enemy DEF up pulls the light in). **Typing waits (user 2026-10-18):** the card rebuilds on every keystroke, but `heroDelta` holds the comparison (`statTyping`, `deltaHeld`, like the pop-ups) and the changed chips keep showing their old values until the typing is done (800 ms without a keystroke, Enter, or leaving the field: `change`, `statTypingFlush`); then one volley plays against the values from before the first keystroke. Only trusted keystrokes hold it: a value written by code (target solve, presets, enemy picks) plays at once. Several stats at once (an enemy pick) go to the clicked-control branch below instead. Flicker lengths: ping 1.1 s, text 1.6 s. **Flashes survive rebuilds (user 2026-10-05):** `pingField` stamps `data-ping-cls` / `data-ping-at`; `renderHero()` notes every field still flashing (`pingCarryCapture`, same skill only), and after `renderHeroNow()` the field at the same place resumes with a negative `animation-delay` (`pingCarryApply`). A comet in flight resolves its target when it lands (`fieldPos` / `liveField`), so a fast second click on the same toggle cuts nothing off. **Colour (user 2026-10-05):** a field that did not get worse lights up (comet + ping `.sk-delta-stat`) in the typed stat's colour when exactly one stat input changed, otherwise in its own chip's stat colour (`statColorFor` / `CHIP_STATS` in `heroDelta`: cooldown AGI, or INT for Phoenix Fireball; cast INT; duration CHA / TAL; `sk-stat-lck*` LCK; damage chips ATK / TAL / DEF / ...; only stats `getUsedPlayerStatKeys` / `getUsedEnemyStatKeys` report for the skill, a stat whose input just changed first, so an enemy pick colours damage DEF). Gold only for fields with no stat (desc text, costs, odds chips). The **KO badge** (`.sk-ko-badge`) is its own field (user 2026-10-06): the damage formula chip's text leaves it out (`deltaText` drops `.sk-ko-badge`), so a skill dep or input that only moves KO sends the light to the badge, not the whole formula / damage row; higher KO = better, gold (no stat), cost-badge flash style, value from `.sk-ko-value`. The summon stat block is not a field; each `.sk-summon-stat` row is (in the chip group, value from `.sk-summon-stat-value`, higher = better), so every changed summon stat gets its own comet in its own colour (HP = VIT colour, MAG = INT). Worse is always red, typing included. When any `.sk-dmg-formula` in a `.sk-dmg-row` changed, the row's changed chips are replaced by the row itself (formula + Raw + Final = one comet); on impact `pingField` flashes the row's chips together, each inside its own border, never the row block or the gaps between chips (the chips' solid backgrounds hide a flash on the row). Deps in `WORSE_WHEN_ON` (inside `heroDelta`: `wolfKatana`, `rabW59`, `catW59`, `mnkW59`, `pgnW59`, `batW59`, all ×0.75 weapons) count as worse when switched on (red comets in) and better when switched off; the flip class follows the button's real on-state: off → on `.sk-dep-flip-on`, on → off `.sk-dep-flip-off`, a rank change that stays on (or off) `.sk-dep-flip-swap`. Since 2026-10-07 (user) these are no longer flips: all three are the same 0.3 s scale pop (1 > 1.07 > 1); `-on` / `-off` also fade the colour in / out during it (no light slide: user dropped it, a masked sweep was not visible enough) (turns over, no lighting change). The rebuilt button already has its new icon (max rank → off is the rank-1 picture), so `flipStart` puts the old `src` back and swaps it in when the animation delay ends (`FLIP_MID` is 0 for all three). The clicked dep button always flips, even when its icon and stored rank don't change (capture-phase click on `displayEl` → `depClicked`). Desc numbers, status keywords and the formula chip are unreadable and follow the source. All sources go through one `volley(c, srcUp, {tone, outDelay})`; it returns the last inward landing time, used for the worse dep icon's delayed flip.   * **Hold:** right after a rebuild, `rollHoldAll(prev)` (top of `heroDelta`, which runs before the first paint) freezes every changed chip value at its old value (`rollHold`: the new value laid out but hidden in `.sk-roll-new`, the old one drawn over it in `.sk-roll-old`; a 4 s safety timer always lets go). A number never shows its new value before its light lands. The snapshot keeps each field's value markup for this (`htmls`, via `rollHtmls`). The old value and the coloured copy are aligned like the value itself (flex, `--roll-jc` from its `text-align`, content in `.sk-roll-in`). The first of four spots that stays inside the chip and clear of its other text wins:

      2. raised over the number's end
      3. just under that end
      4. the chip's top-right corner, level with the label (`.is-corner`). Used on narrow phone chips, where the number ends near that edge anyway.

    * **Changes in a row (user 2026-10-18: merge the clicks that beat the first pill; a click after it appears respects that pill as a whole, then plays its own):**
      * **Base:** a chip that changes keeps showing the value it had on screen until its change plays, through every rebuild in between (`rollBase`, keyed by skill and chip place via `chipKey`, since every click rebuilds the chips). The value on screen is the snapshot's, or the last played one (`rollShown`) when it played after the snapshot was taken (a held typing snapshot is older). A chip back at its base lets go; a base older than 4 s (the hold's safety limit) is dropped; a skill switch clears all of it.

      * **Hand-over:** a change landing while a pill shows waits (`handOver`; one waiting change per field, and later clicks merge into it). ## Popup performance (2026-10-14, user)

* **No `backdrop-filter` on any overlay or popup.** A full-viewport `backdrop-filter: blur()` makes the browser re-blur the whole (huge, scaled) page behind it on every frame while the popup animates in; the server-balance popup and the Buff / Debuff panel lagged very hard until the blurs were removed. Dim the page with a plain `rgba()` background (raise the alpha a little to compensate). A second blur on a ~98%-opaque popup panel is invisible and pure cost. Validator `[PERF ERROR]` fails on any `backdrop-filter` other than the theme variable `var(--th-blur,none)`.
* **Animate `transform` and `opacity` only** (the popup pop-in does). Keyframes on `box-shadow`, `filter`, `background` or layout properties repaint every frame; keep them short (the delta pings) and never `infinite` on the main page. Known leftovers: `simGlow` on `.sk-simulate-btn.is-new` (infinite `box-shadow`, only until the first Test click).
* A popup must not rebuild or re-render more than it shows: `renderBdPopup` rebuilds its whole `innerHTML` (every item's data-URI `<img>`) on each toggle and `renderHero()` follows; measured ~5 ms per click, fine today, but do not add more work there.

## Target value on a stat chip (2026-10-08, user)

* Clicking a **Cooldown / Cast Time / Duration / chance** chip (`.sk-target-chip`: pointer cursor; on hover only the number glows (`text-shadow`), no chip fill and no transform because the stat tooltips are `position:fixed`, no icon; chips with no stat effect, `.sk-stat-value.unwrapped`, are not clickable) edits **in place** (`openTargetEdit`): the chip's coloured number is swapped for an input that inherits its font and colour (no box, no range hint, no buttons). Enter or clicking / tapping away confirms (an unchanged or invalid value just closes), Esc cancels. The reachable range, the flat check and the clamping are checked on confirm and reported by the toast. The user types the value they want; it is clamped to what the formulas can reach, then the smallest stat that gets there is written into that stat's input: CD → AGI, cast → INT, duration → CHA (TAL with `durAdjust:"tal"`), chance → LCK. Phoenix / Monkey own-stat cooldowns are skipped.
* **How it solves** (`solveTarget`): it does not re-implement the formulas. It binary-searches the stat (0 .. 512; **AGI has no cap**: the search widens ×4 up to a 1,000,000 limit, so it can run wild), each step typing the stat in, setting LCK = 0 (no luck spread, so the chip shows one number) and calling `renderHeroNow()`, then reads the chip (`chipNumber`: the worse end of a range). Dependencies, Revised Art, buffs and the enemy target are respected for free. **The direction is measured, not assumed** (`targetRange` compares the chip at stat 0 and at the cap, `info.dec`): Bat Doom's duration is contested the inverted way (more CHA = shorter), flat post-added durations and floored steps (cast time falls in whole seconds) come out right because the chip itself is the formula. Checked on every chip of all 625 skills (no errors; cast time lands on the whole second at or below the wanted value). `withProbe` restores the stat and LCK and re-renders, so the card's real state, and the delta-motion snapshot, are the original ones before the real change is made.
* **Side effects (user decision):** only the one stat input changes; LCK keeps its real value. The write is a real `input` event (card re-renders with the delta motion, the preset autosaves) preceded by `presetPushUndo()`, so **Ctrl+Z** restores it. A toast (`.sk-target-toast`) says what changed, or that the value was clamped / the chip does not depend on the stat.
